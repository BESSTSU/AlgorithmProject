## 4. ภาพรวมโปรเจค

วางแผนเส้นทางให้หุ่นยนต์หลายตัวใช้ทางเดินร่วมกันไปทำงานตามห้องโดยไม่ชนกัน ภายใต้แบตเตอรี่และช่องชาร์จที่มีจำกัด
ทดสอบใน simulation ให้ครบก่อน แล้วขึ้นหุ่นจริง TurtleBot3 Burger 2 ตัว (ROS 2 Humble) ซึ่งทำสำเร็จแล้ว

**จุดเน้นของโปรเจค 2 ข้อ**

1. **การชาร์จเป็น action ภายใน search**: planner คิดล่วงหน้าทั้งลำดับงานว่าควรชาร์จตอนไหนและนานเท่าไร แทนการรอให้แบตต่ำแล้วค่อยไป
2. **ช่องชาร์จเป็นทรัพยากรที่ต้องจอง**: ช่องชาร์จอยู่ใน reservation table เหมือนช่องทางเดิน หุ่นจึงไม่แย่งกันและไม่ยืนรอคิวขวางทางเดิน

พิสูจน์ด้วยการเทียบกับ baseline แบบกฎตายตัวบนแมพ ฉาก ลำดับความสำคัญ และ horizon เดียวกัน ต่างกันแค่วิธีตัดสินใจชาร์จ

**แมพหลัก (สนามจริง 6×5 ช่องละ 0.45 m สนามกว้าง 2.7 × 2.25 m)**

```
AA####
AA##.#
.....C
###BB#
###BB#
walls: (1,0)-(2,0) (2,4)-(3,4)
```

`A`, `B` = ห้อง, `.` = ทางเดิน, `C` = ช่องชาร์จ (2,5) ที่ปลายตัน, `#` = นอกสนาม, `walls:` = กำแพงบางบนขอบช่อง พิกัดเป็น (row, col)
ห้อง A ต่อกับทางเดินทางเดียวที่ (1,1)↔(2,1) ห้อง B ทางเดียวที่ (2,3)↔(3,3) ทางเดินแถว 2 สวนกันไม่ได้

## 5. อัลกอริทึมในการตัดสินใจ (เนื้อหาหลักของรายงาน)

การตัดสินใจมี 3 ชั้น คือ **หุ่นแต่ละตัวไปทางไหนและชาร์จเมื่อไร** (Space-time A*), **ใครได้ก่อนเมื่อทางทับกัน** (Prioritized Planning + reservation table)
และ **ตอนรันจริงใครขยับได้เมื่อไร** (ADG) ไฟล์อ้างอิงอยู่ในวงเล็บ

### 5.1 โมเดลเวลาและแบต (`core/battery.py`)

เวลาเป็นก้าวไม่ต่อเนื่อง ทุก action ใช้ 1 ก้าว: เดิน 4 ทิศ หรือ wait ไม่เดินทแยง

| พารามิเตอร์ | ค่า | ความหมาย |
|---|---|---|
| `max` | 40 | แบตเต็ม |
| `move_cost` | 2 | เดินหนึ่งก้าว |
| `wait_cost` | 1 | รอหนึ่งก้าว |
| `charge_rate` | +5 | wait บนช่องชาร์จ = ชาร์จ (ไม่เกิน `max`) |
| `min_final` | 10 | แบตขั้นต่ำเมื่อจบงานสุดท้าย |
| `reserve` | 0 (รันจริงใช้ 5) | แบตขั้นต่ำที่ต้องรักษาทุกก้าว เผื่อความล่าช้า |

### 5.2 Space-time A* แบบมีแบตและหลายงาน (`core/st_astar.py`)

- **State** = `(cell, t, battery, k)` โดย `k` คือดัชนีงานถัดไป การรวม `k` ไว้ใน state ทำให้การตัดสินใจชาร์จมองงานทั้งลำดับ
- **g** = t, **h** = ระยะ Manhattan ไปเป้าหมายงาน k บวกระยะระหว่างเป้าหมายที่เหลือ (admissible)
- **Action**: อยู่กับที่ (รอหรือชาร์จ) หรือเดินไปช่องข้างเคียง ไม่มี action "ชาร์จ" แยกต่างหาก
- **Dominance pruning**: ที่ `(cell, t, k)` เดียวกัน state ที่แบตมากกว่าทำได้ทุกอย่างที่ตัวแบตน้อยทำได้ จึงขยายแค่ตัวที่แบตมากสุด
  (SPEC บันทึกว่าเร็วขึ้นประมาณ 10 เท่า และเทียบแล้วได้คำตอบเหมือนเวอร์ชันพื้นฐาน)
- **เงื่อนไขจบ**: ทำครบทุกงาน อยู่ที่เป้าหมายสุดท้าย แบต ≥ `min_final` และไม่มีหุ่นตัวอื่นจองช่องนั้นหลังจากนี้ (จอดค้างได้ปลอดภัย)
- **Horizon** `t_max` = 200 เกินแล้วคืนค่าว่าหาทางไม่ได้

```
open ← { start } เรียงตาม f = t + h
while open ไม่ว่าง:
    (cell, t, level, k) ← pop ตัวที่ f น้อยสุด
    ข้ามถ้ามี state ที่แบตมากกว่าที่ (cell, t, k) เดียวกัน
    ถ้า k ครบ และอยู่เป้าหมายสุดท้าย และ level ≥ min_final และช่องนี้ไม่ถูกจองอีก: คืนเส้นทาง
    ถ้า t ≥ t_max: ข้าม
    สำหรับ next ใน { cell (รอ/ชาร์จ) } ∪ ช่องข้างเคียง:
        ข้ามถ้า next ถูกจองที่ t+1
        new_level ← กฎแบต (เดิน −2, รอ −1, รอบนช่องชาร์จ +5)
        ข้ามถ้า new_level < reserve
        new_k ← เพิ่ม k ถ้า next คือเป้าหมายของงาน k
        ข้ามถ้ามี state ที่แบตเท่ากันหรือมากกว่าที่ (next, t+1, new_k) แล้ว
        ใส่ state ใหม่ลง open
คืนค่า "หาทางไม่ได้"
```

เมื่อหาทางไม่ได้ ระบบบอกสาเหตุ: `battery` (มีทางถ้าไม่คิดแบต), `horizon` (มีทางแต่เกิน `t_max`), `no_path` (ทางถูกปิดถาวร)

### 5.3 Reservation table (`core/reservation.py`)

- หุ่นที่อยู่ช่อง c ที่เวลา t กันช่องนั้นไว้ที่ `t−1`, `t`, `t+1` หุ่นอื่นจึงเข้าช่องในก้าวเดียวกับที่ตัวหน้าออกไม่ได้
- ไม่ต้องจองขอบแยก เพราะระยะเว้น 1 ก้าวครอบคลุมกรณีสลับช่องกันแล้ว
- ช่องเริ่มต้นของหุ่นที่ยังไม่ได้วางแผนถูกกันไว้ที่ `t = 0` และ `t = 1`
- หุ่นที่เสร็จแล้วจองช่องสุดท้ายยาวไปถึง `t_max`
- ช่องชาร์จจองแบบเดียวกับช่องอื่น จึงมีหุ่นอยู่ได้ทีละตัวโดยไม่ต้องมีกลไกพิเศษ

### 5.4 Prioritized Planning (`core/prioritized.py`)

วางแผนทีละตัว ตัวถัดไปเลี่ยงทุกอย่างที่ตัวก่อนหน้าจองไว้ มี 3 กลยุทธ์จัดลำดับ

- `fixed`: ตามหมายเลขหุ่น
- `battery_urgency`: แบตน้อยได้ก่อน
- `random_restart`: ลองลำดับเดิม ถ้าไม่ได้สุ่มลำดับใหม่สูงสุด 10 ครั้ง

ข้อจำกัดที่ควรบอกในรายงาน: Prioritized Planning ไม่ complete ลำดับที่เลือกอาจทำให้หาทางไม่ได้ แม้มีคำตอบอยู่จริง (ไม่ได้ทำ CBS เทียบ อยู่ในรายการทำทีหลัง)

### 5.5 Baseline กฎตายตัว (`core/baseline.py`)

ใช้ Space-time A*, reservation table และ Prioritized Planning ชุดเดียวกัน แต่ปิดการชาร์จใน search
ก่อนเริ่มแต่ละงาน ถ้าแบต < เกณฑ์ ให้แทรกช่วง "ไปช่องชาร์จที่ใกล้ที่สุด (วัดด้วย BFS) ชาร์จจนเต็ม" แล้วค่อยทำงาน
ทดลองเกณฑ์ 30%, 50%, 70% และ 100% (100% = ชาร์จเต็มก่อนทุกงาน)

### 5.6 การรันแผนด้วย Action Dependency Graph (`execution/adg.py`, `execution/executor.py`)

แผนผูกกับเวลา แต่หุ่นจริงเดินช้าเร็วไม่เท่ากัน ถ้ารันตามนาฬิกาแผนจะพังทันที จึงเก็บแค่ **ลำดับ** ทิ้งการรอในแผน

- หุ่น i เข้าช่อง c ได้ก็ต่อเมื่อหุ่นที่แผนกำหนดให้ผ่าน c ก่อนหน้า ได้เดินออกจาก c จนจบการเคลื่อนที่แล้ว
- ลำดับการผ่านทุกช่องจึงเหมือนในแผนเสมอ ไม่ว่าใครช้าหรือเร็ว
- ที่ช่องชาร์จ หุ่นอยู่อย่างน้อยเท่าเวลาตามแผน และจนกว่าแบตจริงถึงระดับที่แผนตั้งไว้ตอนออก
- ถ้าไม่มีหุ่นตัวไหนขยับต่อได้ executor แจ้ง deadlock
- 1 ก้าวของแผน = 4 วินาที ใช้แปลงเวลาจริงเป็นค่าแบต

### 5.7 โหมดรับงานต่อเนื่อง สำหรับเดโม (`execution/lifelong.py`)

หุ่นได้งานใหม่ทันทีที่ถึงเป้าหมาย ตัวที่ถึงก่อนถูกวางแผนใหม่จากช่องที่ยืนอยู่ โดยจองเส้นทางที่เหลือของตัวอื่นไว้ก่อน แล้วสร้าง ADG ใหม่ ตัวอื่นวิ่งต่อไม่หยุด
ก่อนใช้แผนใหม่ตรวจซ้ำทุกช่วงเวลาว่าไม่ชน ถ้าวางแผนไม่ได้ หุ่นรอบนเป้าหมายแล้วลองใหม่เมื่อตัวอื่นถึงเป้าหมาย
โหมดนี้ใช้แบตสมมุติแยกต่างหาก (`lifelong.battery`: เต็ม 20, เดินช่องละ 1, รอไม่เสีย, ชาร์จ +8 ต่อก้าว, ชาร์จจนเต็ม) **อย่าปนกับค่าในหัวข้อ 5.1**

### 5.8 ตัวอย่างการตัดสินใจ: ฉาก S0 (`scenarios/s0.yaml`)

R1 เริ่ม (2,0) แบต 18 งานคือ (4,4) / R2 เริ่ม (2,4) แบต 40 งานคือ (0,0) งานของ R1 ใช้แบต 22 ซึ่งมากกว่าที่มี จึงต้องอ้อมไปชาร์จก่อน แผนจริงจากโค้ด (`priority: fixed`):

## 6. ผลการทดลอง

ทุกเงื่อนไขมี 50 ฉาก (seed คงที่ 42 ทุกวิธีใช้ชุดฉากเดียวกัน) **ไม่มีการชนเลยในทุกการรัน** รวมถึงรอบที่ใส่ความล่าช้าแบบสุ่ม (20 รอบต่อแผน)
ฉากที่เป็นไปไม่ได้ตั้งแต่ต้นถูกคัดออกแล้ว การเทียบเวลาทำเฉพาะบนฉากที่ทั้งสองวิธีสำเร็จ ผลรันเมื่อ 2026-10-12

## 7. ผลบนหุ่นจริง

ฮาร์ดแวร์: TurtleBot3 Burger 2 ตัว, Raspberry Pi 4, LiDAR LDS-02, ROS 2 Humble (โน้ตบุ๊กรันใน WSL2 Ubuntu 22.04), เชื่อมผ่าน Wi-Fi hotspot
ระบบ: แมพ nav2 วาดจากไฟล์กริด (ลอง SLAM แล้วแมพเพี้ยน), AMCL และ map server รันบน Pi แต่ละตัว, คุมหุ่นแบบหมุนแล้วเดินตรงทีละช่อง ที่ 0.15 m/s

| วันที่ | การรัน | ผล |
|---|---|---|
| 2026-10-15 | S0 หุ่นจริงสองตัว | R1 ถึง (4,4) 64.0 วินาที (แผน 52), แบตต่ำสุด 6.6, ชาร์จที่ (2,5); R2 ถึง (0,0) 52.3 วินาที (แผน 40); ระยะใกล้สุด 0.416 m |
| 2026-10-15 | เดโมต่อเนื่อง หุ่นจริงสองตัว (แบตสมมุติ 16 ชุดเดิม) | 9 งานใน 4 นาที หลบกันและชาร์จตามแผน |

| 2026-10-29 | เดโมต่อเนื่อง หุ่นจริงสองตัว | 6 งาน (ตัวละ 3), ระยะใกล้สุด 0.401 m |

ทุกรอบไม่มีการหยุดฉุกเฉินจาก `safety_distance` และจบเพราะเจ้าของโปรเจคปิดหน้าต่างเอง ไม่ได้จบเพราะระบบล้ม

**ระบบความปลอดภัยที่มีจริง**

- หุ่นสองตัวเข้าใกล้กันต่ำกว่า 0.30 m: หยุดทุกตัวและจบการรัน
- watchdog บน Pi: คำสั่งขาดเกิน 0.5 วินาที หุ่นหยุดเอง (ทดสอบจริง หยุดใน 0.76–0.86 วินาที)
- ตำแหน่งไม่อัปเดตเกิน 1 วินาที: หุ่นตัวนั้นหยุดรอ
- ไม่ออกตัวถ้าหุ่นไม่อยู่บนช่องเริ่มต้น และทุกทางออกของโปรแกรมส่งคำสั่งหยุด

**ปัญหาที่เจอและวิธีแก้** (เหมาะกับหัวข้ออภิปรายผล)

- SLAM แมพเพี้ยนเพราะทางเดินตรงมีกำแพงขนานหน้าตาเหมือนกันทั้งเส้น จึงวาดแมพจากไฟล์กริดแทน
- `turtlebot3_node` ไม่มี timeout ของคำสั่ง Wi-Fi หลุดแล้วหุ่นวิ่งต่อ จึงเพิ่ม watchdog
- AMCL บนโน้ตบุ๊กไม่นิ่งบน hotspot ที่ช้า (scan มาถึงราว 3 Hz จาก 9–10 Hz, นาฬิกาต่างกันราว 1 วินาที) จึงย้าย AMCL ไปบนหุ่น
- Ctrl+C ถูกลูปของหน้าต่าง GUI กลืน โปรแกรมไม่หยุด จึงแก้ให้ลูปควบคุมเช็คธงหยุดทุก tick
- `--localize` บอก OK ได้แม้วางหุ่นผิด (หันกลับ 180° หรือผิดช่องในทางเดิน) จึงต้องเช็คว่า scan ทับแมพก่อนรันทุกครั้ง

## 9. ข้อจำกัดที่ต้องเขียนตรงๆ

- **หุ่นมองไม่เห็นคนหรือสิ่งกีดขวางที่ไม่อยู่ในแมพ** LiDAR ใช้ระบุตำแหน่งเท่านั้น ถ้าคนยืนขวาง หุ่นจะดันต่อและระบบค้างรอ ตอนนี้ไม่มีการหลบหรือวางแผนใหม่กลางทาง
- แบตเป็นแบตจำลอง ไม่ได้วัดจาก LiPo จริง
- `execution.step_seconds` = 4 ตั้งไว้ตอนช่อง 0.5 m ยังไม่ได้วัดใหม่สำหรับช่อง 0.45 m หุ่นจริงใช้เวลามากกว่าแผน 12 วินาทีในทั้งสองตัวของ S0
- ยังไม่เคยรันเดโมบนหุ่นจริงสองตัวต่อเนื่องนานเกินราว 4 นาที
- เวลาใน log ของเดโม นับจากรอบของลูปควบคุม ตอนเปิดหน้าต่างแสดงผล เวลาจริงนานกว่าราว 1.3 เท่า
- บน hotspot ที่ช้าหรือแบตหุ่นอ่อน การสื่อสารหลุดเป็นช่วง
- Prioritized Planning ไม่ complete และไม่รับประกันคำตอบที่ดีที่สุดของทั้งทีม

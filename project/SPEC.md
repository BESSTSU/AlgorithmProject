# สเปกโปรเจค: Battery-aware Multi-Robot Path Planning

> เอกสารนี้คือข้อกำหนดของระบบทั้งหมด ใช้ส่งต่อให้ Claude Code เขียนโค้ด
> ค่าตัวเลขที่ระบุว่า "ค่าเริ่มต้น" ปรับได้ แต่ให้ถามเจ้าของโปรเจคก่อนเปลี่ยน
>
> ปรับปรุง 2026-10-11 ให้ตรงกับโค้ดหลังจบ M6 (หัวข้อ 3, 4, 5, 6, 8, 10.3, 11, 12)
> เป้าหมายหลักคือรันบนหุ่นจริง 2 ตัว การทดลองกับหุ่นมากกว่า 2 ตัวทำใน simulation เท่านั้น

## 1. เป้าหมาย

โปรเจครายวิชา (ไม่ใช่ธีสิส) วางแผนเส้นทางให้หุ่นยนต์หลายตัว (ตั้งต้น 2 ตัว) ใช้ทางเดินร่วมกัน
ไปทำงานตามห้องต่างๆ โดยไม่ชนกัน ภายใต้ข้อจำกัดแบตเตอรี่และสถานีชาร์จที่มีจำกัด

ระบบทั้งหมดออกแบบให้รันบนหุ่นจริง (TurtleBot3 Burger 2 ตัว) ได้ แต่ **ทดสอบบน simulation ให้ครบก่อน**
ทั้งตัวอัลกอริทึมและการทำงานทั้งระบบ แล้วจึงขึ้นหุ่นจริงเป็นขั้นสุดท้าย

## 2. จุดขายของงาน (key contribution)

ฐานของงานคืออัลกอริทึมที่มีอยู่แล้ว ได้แก่ Space-time A\* + Prioritized Planning + reservation table
ส่วนที่เป็นจุดเน้นของโปรเจคคือ:

1. **การชาร์จเป็น action ภายใน search**: planner คิดล่วงหน้าทั้งลำดับงานว่าควรชาร์จตอนไหนและนานเท่าไร
   แทนที่จะรอให้แบตต่ำแล้วค่อยไปชาร์จ
2. **ช่องชาร์จเป็นทรัพยากรที่ต้องจอง**: ช่องชาร์จอยู่ใน reservation table เหมือนช่องทางเดิน
   หุ่นจึงไม่แย่งกันและไม่ยืนรอคิวขวางทางเดิน

พิสูจน์ด้วยการเทียบกับ **baseline แบบกฎตายตัว** (แบตต่ำกว่า 30% ให้ไปชาร์จเต็ม)
บนแมพ ฉากทดสอบ ลำดับความสำคัญ และ horizon เดียวกันทุกอย่าง ต่างกันแค่วิธีตัดสินใจชาร์จ

หมายเหตุ: งานวิจัย MAPF ที่มีข้อจำกัดพลังงานมีอยู่แล้ว ห้ามเขียนในรายงานหรือคอมเมนต์ว่า "ไม่มีใครทำมาก่อน"
ให้ใช้คำว่า "จุดเน้นของโปรเจคนี้"

## 3. แมพทดสอบหลัก (challenge map 11×5)

ไฟล์ `maps/challenge_11x5.txt` พิกัดเป็น (row, col) จุดเริ่มมุมซ้ายบน

```
AAA##BBB###
AAA##BBB###
#D####D####
..........C
######.####
```

| สัญลักษณ์ | ความหมาย |
|---|---|
| `#` | กำแพง (เดินไม่ได้) |
| `.` | ทางเดิน / ช่องหลบ |
| `A`, `B` | ช่องในห้อง A, ห้อง B (เดินได้ ใช้ระบุเป้าหมาย) |
| `D` | ช่องประตู (เดินได้) |
| `C` | ช่องชาร์จ (เดินได้ มีได้ทีละ 1 ตัว) |

ความท้าทายที่ตั้งใจใส่ไว้:
- ทางเดินเดียว (แถว 3) หุ่นสองตัวสวนกันผ่านพร้อมกันไม่ได้
- ช่องหลบมีน้อย: ประตู (2,1), (2,6) และช่องข้างทาง (4,6)
- สถานีชาร์จ 1 ช่องที่ (3,10) อยู่ปลายตัน ตัวที่รอชาร์จจะขวางทางเดิน

**ฉากอ้างอิง S0** (ตรงกับภาพในสไลด์):
- R1: เริ่ม (3,2) แบตต่ำ งาน = [ห้อง B ช่อง (0,6)]
- R2: เริ่ม (3,8) แบตเต็ม งาน = [ห้อง A ช่อง (0,1)]
- ให้ Claude Code ปรับแบตเริ่มต้นของ R1 จนได้คุณสมบัตินี้ แล้วเขียนเทสยืนยัน:
  **R1 ทำงานไม่สำเร็จถ้าไม่แวะชาร์จ แต่สำเร็จเมื่อแวะชาร์จ** และ R2 ต้องหลบให้ R1 ในทางเดิน
  (คำนวณคร่าวๆ ด้วยค่าเริ่มต้นในหัวข้อ 4.2 โดยไม่นับการรอ: แบตเริ่มต้นของ R1 ควรอยู่ช่วง 16–23)
- ค่าที่ใช้จริง (ไฟล์ `scenarios/s0.yaml`): R1 แบตเริ่ม 20, R2 แบตเริ่ม 40
  เทสยืนยันแล้วว่าทั้งช่วง 16–23 มีคุณสมบัตินี้ (15 ไปไม่ถึงช่องชาร์จ, 24 ไม่ต้องชาร์จ)
  แผนที่ได้: R1 ไปชาร์จ 4 ก้าวแล้วไปห้อง B รวม 19 ก้าว, R2 หลบเข้าประตู (2,6) รวม 14 ก้าว
- ถ้าตั้ง `battery.reserve` = 5 (หัวข้อ 4.2) ช่วงที่ใช้ได้จะแคบลงเป็น 21–23

**แมพที่สอง** `maps/loop_13x6.txt` ใช้ทดลองเพิ่มจำนวนหุ่น (2 → 3 → 5) **ใน simulation เท่านั้น**
หุ่นจริงมี 2 ตัวและใช้แมพ 11×5

```
AAA##BBB##EEE
AAA##BBB##EEE
#D####D####D#
.............
.###C###C###.
.............
```

มี 3 ห้อง ทางเดิน 2 เส้นเชื่อมกันเป็นวง และช่องชาร์จ 2 ช่องอยู่บนทางเชื่อมระหว่างสองทางเดิน
ระบบโหลดแมพจากไฟล์ จึงเพิ่มแมพใหม่ได้โดยไม่แก้โค้ด

## 4. อัลกอริทึม

### 4.1 โมเดลเวลาและการกระทำ
- เวลาเป็นก้าวไม่ต่อเนื่อง t = 0, 1, 2, ...
- ทุก action ใช้เวลา 1 ก้าว: เดิน 4 ทิศ หรือ wait
- **ที่ช่องชาร์จ action wait = ชาร์จ** (แบตเพิ่ม) จึงไม่ต้องมี action แยก
  ถ้าแบตเต็มแล้ว wait ที่ช่องชาร์จไม่เสียแบต (แบตคงที่ที่ `battery_max`)

### 4.2 แบตเตอรี่ (ค่าเริ่มต้น ปรับใน config)
| พารามิเตอร์ | ค่าเริ่มต้น |
|---|---|
| `battery_max` | 40 หน่วย (จำนวนเต็ม) |
| `move_cost` | 2 ต่อก้าว |
| `wait_cost` | 1 ต่อก้าว |
| `charge_rate` | +5 ต่อก้าว (ไม่เกิน `battery_max`) |
| `min_final_battery` | 10 (แบตขั้นต่ำเมื่อจบงานสุดท้าย) |
| `reserve` | 0 (แบตขั้นต่ำที่ planner รักษาไว้ทุกก้าว เผื่อความล่าช้าตอนรันจริง) |

กฎ: แบตห้ามต่ำกว่า `reserve` ในทุกขณะ state ที่ต่ำกว่าให้ตัดทิ้ง (ค่าเริ่มต้น 0 คือห้ามติดลบ)
การทดลองเทียบ `reserve` = 0 กับ 5 ส่วนการรันบนหุ่นจริงควรใช้ค่ามากกว่า 0 (ดูผลในหัวข้อ 8)

### 4.3 Space-time A\* แบบมีแบตและหลายงาน (หัวใจของงาน)
- **State** = `(row, col, t, battery, k)` โดย `k` คือดัชนีงานถัดไปที่ต้องทำ
  ถึงช่องเป้าหมายของงาน k แล้ว k เพิ่มขึ้น 1
  การรวม k ไว้ใน state ทำให้ planner ตัดสินใจเรื่องชาร์จโดยมองงานทั้งลำดับ ซึ่งคือจุดขายข้อ 1
- **g** = t (เวลาที่ใช้)
- **h** = ระยะ Manhattan จากตำแหน่งปัจจุบันไปเป้าหมายงาน k บวกระยะระหว่างเป้าหมายที่เหลือตามลำดับ (admissible)
- **Closed set** ใช้คีย์ `(row, col, t, battery, k)` ห้ามใช้แค่ `(row, col)`
  เพราะจะทิ้ง action wait ที่จำเป็นในการหลบ
- **Dominance pruning (ทำแล้ว)**:
  ที่ `(row, col, t, k)` เดียวกัน state ที่แบตมากกว่าดีกว่า ตัดตัวที่แบตน้อยกว่าทิ้งได้
  เร็วขึ้นประมาณ 10 เท่า และเทียบแล้วได้คำตอบเหมือนเวอร์ชันพื้นฐาน
- **เงื่อนไขจบ**: ทำครบทุกงาน อยู่ที่เป้าหมายสุดท้าย แบต ≥ `min_final_battery`
  และไม่มีหุ่นตัวอื่นจองช่องนั้นในเวลาใดๆ หลังจากนี้ (จอดค้างได้อย่างปลอดภัย)
- **Horizon** `t_max` (ค่าเริ่มต้น 200) เกินแล้วคืนค่า "หาทางไม่ได้" ห้ามวนไม่จบ

### 4.4 Reservation table
- **จองจุดพร้อมระยะเว้น 1 ก้าว**: หุ่นที่อยู่ช่อง c ที่เวลา t จะกันช่องนั้นไว้ที่ `t−1`, `t` และ `t+1`
  หุ่นตัวอื่นจึงเข้าช่องในก้าวเดียวกับที่ตัวหน้าออกไม่ได้ ซึ่งเป็นกฎเดียวกับที่ executor ใช้ (หัวข้อ 6)
  แผนจึงรันได้ตรงตามแผนเมื่อไม่มีความล่าช้า
- **ไม่มีการจองขอบแยก**: ระยะเว้น 1 ก้าวครอบคลุมกรณีสองตัวสลับช่องกันอยู่แล้ว
- **ช่องเริ่มต้น**: ช่องเริ่มต้นของหุ่นที่ยังไม่ได้วางแผนถูกกันไว้ที่ `t = 0` และ `t = 1`
  เพราะหุ่นตัวนั้นยังออกจากช่องไม่ทัน
- **จอดหลังเสร็จงาน**: หุ่นที่เสร็จแล้วจองช่องสุดท้ายตั้งแต่เวลาที่ถึงไปจนถึง `t_max`
- **ช่องชาร์จ**: เป็นช่องหนึ่งบนแมพ จองผ่านการจองจุดได้เลย สถานีหลายช่องให้แทนด้วยหลายช่อง `C`

### 4.5 Prioritized Planning
วางแผนทีละตัวตามลำดับความสำคัญ ตัวถัดไปต้องเลี่ยงทุกอย่างที่ตัวก่อนหน้าจองไว้
กลยุทธ์จัดลำดับ (เลือกใน config เพื่อใช้ทดลองเปรียบเทียบ):
- `fixed`: ตามหมายเลขหุ่น
- `battery_urgency`: แบตน้อยได้ก่อน
- `random_restart`: ถ้าหาทางไม่ได้ ให้สุ่มลำดับใหม่ได้สูงสุด N ครั้ง

### 4.6 Baseline (กฎตายตัว)
- ใช้ Space-time A\* และ reservation table ชุดเดียวกัน
- **ปิดการชาร์จใน search** (wait ที่ช่องชาร์จไม่เพิ่มแบต) ยกเว้นในช่วงชาร์จที่กฎแทรกให้
- ก่อนเริ่มแต่ละงาน ถ้าแบต < 30% ของ `battery_max` ให้แทรกช่วง "ไปช่องชาร์จที่ใกล้ที่สุด ชาร์จจนเต็ม"
  แล้วค่อยทำงานนั้น
- วางแผนทีละช่วงต่อกัน ถ้าแบตจะติดลบระหว่างช่วงใด นับเป็น "ล้มเหลวเพราะแบตหมด"
- รายละเอียดที่ตกลงเพิ่ม:
  - "ช่องชาร์จที่ใกล้ที่สุด" วัดด้วยระยะทางเดินจริง (BFS) ไม่ใช่ Manhattan
  - ถ้าช่องชาร์จไม่ว่าง baseline ไปให้ถึงเร็วที่สุดเท่าที่การจองยอม และรอระหว่างทาง
  - baseline ต้องเหลือแบต ≥ `min_final_battery` ตอนจบเหมือนวิธีหลัก ถ้าไม่ถึงนับเป็นล้มเหลวเพราะแบต
  - ใช้ Prioritized Planning ตัวเดียวกับวิธีหลัก ต่างกันแค่ตัววางแผนต่อหุ่นหนึ่งตัว
- การทดลองใช้หลายเกณฑ์ (30%, 50%, 70%, 100%) แล้วเทียบวิธีหลักกับเกณฑ์ที่ดีที่สุด
  เกณฑ์ 100% คือชาร์จเต็มก่อนทุกงาน

### 5.1 RobotInterface
ระดับคำสั่งคือ "ช่อง" ไม่ใช่ความเร็วล้อ ทุก backend ต้องมี:
- `get_cell()` ช่องปัจจุบัน
- `go_to_cell(cell)` เริ่มเคลื่อนไปช่องข้างเคียง (ไม่บล็อก)
- `is_arrived()` ถึงแล้วหรือยัง
- `get_battery()` ระดับแบต (ใน sim ให้ executor จำลองเอง)
- `stop()`

## 6. การรันแผน (สำคัญต่อการขึ้นหุ่นจริง)

แผนจาก planner ผูกกับเวลา (x, y, t) แต่หุ่นจริงและ CoppeliaSim เดินช้าเร็วไม่เท่ากัน
ถ้ารันตามนาฬิกา แผนจะพังทันที

ให้ executor รันแบบ **เรียงลำดับตามแผน ไม่ผูกนาฬิกา** ด้วย Action Dependency Graph (ADG):
หุ่น i จะเข้าช่อง c (ก้าวที่ k ของแผน) ได้ก็ต่อเมื่อหุ่นทุกตัวที่แผนกำหนดให้ผ่านช่อง c ก่อนหน้านั้น
ได้ออกจากช่อง c ไปจริงแล้ว ลำดับการผ่านแต่ละช่องจึงเหมือนในแผนเสมอ ไม่ว่าใครช้าหรือเร็ว
(คำค้นสำหรับเอกสารอ้างอิง: "action dependency graph MAPF execution")

ใช้ ADG ตั้งแต่ใน sim เลย เพื่อให้สิ่งที่ทดสอบใน sim คือสิ่งเดียวกับที่จะรันบนหุ่นจริง

กฎของ executor ที่ตกลงเพิ่ม:
- การ wait ในแผนถูกทิ้ง เหลือแต่ลำดับการเดิน หุ่นออกเดินได้เมื่อการเดินที่มันขึ้นต่อเสร็จจริงแล้ว
- **แบตจริง** คิดตามสิ่งที่เกิดขึ้น: เริ่มเดินเสีย `move_cost`, ทุก tick ที่รอหรือเดินช้ากว่าปกติเสีย `wait_cost`,
  อยู่บนช่องชาร์จได้ `charge_rate`
- **ที่ช่องชาร์จ** หุ่นอยู่อย่างน้อยเท่าเวลาที่แผนกำหนด และจนกว่าแบตจริงจะถึงระดับที่แผนตั้งไว้ตอนออก
  (planner ชอบให้รอบนช่องชาร์จเพราะไม่เสียแบต ถ้าออกก่อนจะกลายเป็นรอในทางเดินซึ่งเสียแบต)
- แบตจริงที่ติดลบถูกบันทึกไว้เป็นตัววัด แต่ไม่หยุดหุ่น
- ถ้าไม่มีหุ่นตัวไหนขยับต่อได้ executor แจ้ง deadlock
- เมื่อไม่มีความล่าช้า การรันจริงจบตรงเวลาตามแผนพอดี (ตรวจแล้ว 2,671 แผน)
- **ยังไม่ได้ทำ (ต้องทำที่ M7):** executor นับแบตต่อ tick ซึ่งเท่ากับ 1 ก้าวของแผนเฉพาะใน `grid_sim`
  CoppeliaSim และหุ่นจริงต้องมีตัวแปลงหน่วยเวลา (วินาทีต่อ 1 ก้าวของแผน)

## 7. ขั้นการทดสอบ (simulation ก่อนหุ่นจริง)

| ระดับ | สภาพแวดล้อม | ตรวจอะไร |
|---|---|---|
| 0 | `grid_sim` แบบ headless ไม่มีความล่าช้า | อัลกอริทึมถูกต้อง ไม่ชน แบตไม่ติดลบ ใช้รันการทดลองจำนวนมาก |
| 1 | `grid_sim` ใส่ความล่าช้าแบบสุ่ม | ADG + executor ยังปลอดภัยเมื่อหุ่นเดินไม่ตรงเวลา |
| 2 | CoppeliaSim | ตัวควบคุมการเคลื่อนที่ และการแปลงช่อง ↔ พิกัดจริง |
| 3 | TurtleBot จริง | localization การสื่อสาร ของจริงหน้างาน |

ห้ามข้ามระดับ ระดับถัดไปเริ่มได้เมื่อเทสระดับก่อนหน้าผ่านหมด

## 8. ตัววัดผล (บันทึกเป็น CSV ทุกการรัน)
- อัตราสำเร็จ (ทุกตัวทำงานครบ) และสาเหตุที่ล้มเหลว (หาทางไม่ได้ / แบตหมด / เกิน horizon)
- makespan (เวลาที่ตัวสุดท้ายเสร็จ) และ sum of costs (ผลรวมเวลาเสร็จทุกตัว)
- จำนวนก้าวที่รอ (ไม่นับการชาร์จ) และจำนวนก้าวที่ชาร์จ
- จำนวนครั้งที่แวะชาร์จ
- เวลาคำนวณของ planner (ms)
- เฉพาะการรันที่มีความล่าช้า: เวลาเสร็จจริง และจำนวนการชน (ต้องเป็น 0 เสมอ)

ตัวสุ่มฉาก: สุ่มแบตเริ่มต้น จุดเริ่ม และลำดับงานจากช่องในห้อง ใช้ seed คงที่เพื่อให้ผลซ้ำได้
ทุกวิธีต้องรันบนชุดฉากเดียวกัน

รายละเอียดของการทดลองที่ตกลงเพิ่ม:
- **ชุดฉาก**: เก็บเฉพาะฉากที่หุ่นแต่ละตัวทำงานของตัวเองสำเร็จได้ถ้าอยู่ในแมพคนเดียว
  ฉากที่เป็นไปไม่ได้ตั้งแต่ต้นถูกคัดออก
- **สาเหตุที่ล้มเหลว**: `battery` = มีทางภายใน `t_max` ถ้าไม่คิดแบต, `horizon` = มีทางแต่ต้องใช้เวลาเกิน `t_max`,
  `no_path` = ทางถูกปิดถาวร
- **ปัจจัยที่เทียบ**: วิธี (วิธีหลัก และ baseline แต่ละเกณฑ์), กลยุทธ์จัดลำดับ, ค่า `reserve`
  และจำนวนหุ่นบนแมพที่สอง
- **การเทียบ makespan** ทำเฉพาะบนฉากที่ทั้งสองวิธีสำเร็จ
- **แบตจริงติดลบ**: สัดส่วนของรอบที่มีความล่าช้าซึ่งแบตจริงของหุ่นตัวใดตัวหนึ่งต่ำกว่า 0

ผลหลัก (`results/`, 50 ฉากต่อเงื่อนไข, ไม่มีการชนในทุกการรัน):
- แมพ 11×5 หุ่น 2 ตัว: วิธีหลักแก้ได้ 27–33 ฉากตามกลยุทธ์จัดลำดับ baseline แก้ได้ 3–10 ฉากทุกเกณฑ์
  เพราะช่องชาร์จอยู่ปลายตันและไกล
- แมพ 13×6: วิธีหลักแก้ได้ 47 / 47 / 30 ฉากที่ 2 / 3 / 5 ตัว กฎที่ดีที่สุด (100%) แก้ได้ 41 / 30 / 5 ฉาก
  และช้ากว่าวิธีหลัก 1.45–1.79 เท่าบนฉากที่สำเร็จทั้งคู่
- เมื่อมีความล่าช้า แบตจริงของวิธีหลักติดลบ 20% ของรอบที่ `reserve` = 0 และ 3% ที่ `reserve` = 5 (แมพ 11×5)

## 9. Milestones

หลังจบแต่ละ milestone ให้หยุด สรุปสิ่งที่ทำ แสดงผลเทส และรอเจ้าของโปรเจคตกลงก่อนไปต่อ

| # | งาน | เทสที่ต้องผ่าน |
|---|---|---|
| M1 | `grid_map` + Space-time A\* หุ่นตัวเดียว (ยังไม่มีแบต) + แอนิเมชัน | หาทางตรงได้; เลี่ยงกำแพง; คืนค่า "หาทางไม่ได้" เมื่อเกิน horizon |
| M2 | Reservation table + Prioritized Planning | สองตัวสวนกันในแมพ 11×5 แล้วตัวหนึ่งหลบเข้าช่องข้างทาง; ไม่มีการชนแบบช่องเดียวกันและแบบสลับช่อง; หุ่นที่จอดแล้วไม่ถูกเดินทับ |
| M3 | แบต + ชาร์จใน search + หลายงาน (ดัชนี k) | ฉาก S0 ผ่านเงื่อนไขในหัวข้อ 3; แบตไม่ติดลบ; ช่องชาร์จมีได้ทีละตัว |
| M4 | Baseline กฎตายตัว | รันฉาก S0 ได้ และรายงานความต่างจากวิธีหลัก |
| M5 | ADG + executor + `grid_sim` แบบมีความล่าช้า | สุ่ม 1,000 รอบ ไม่มีการชนเลย และทุกตัวถึงเป้าหมาย |
| M6 | ตัวรันการทดลอง + ตัววัด + กราฟ | ได้ CSV และกราฟเทียบวิธีหลักกับ baseline |
| M7 | Backend CoppeliaSim | ฉาก S0 รันในซิมได้ครบโดยใช้ executor ตัวเดียวกับ M5 |
| M8 | Backend TurtleBot3 Burger (ROS 2 Humble) | ทำเมื่อ M7 ผ่าน และตกลงวิธี localization แล้ว (หัวข้อ 12) |

## 10. ฮาร์ดแวร์และสภาพแวดล้อม

### 10.1 ข้อมูลที่ยืนยันแล้ว
- หุ่น: **TurtleBot3 Burger จำนวน 2 ตัว**
- ระบบปฏิบัติการเครื่องหลัก: **Ubuntu 22.04.5** → ใช้ **ROS 2 Humble**
  (คู่ที่ TurtleBot3 รองรับอย่างเป็นทางการ)

สเปก TurtleBot3 Burger จากคู่มือทางการ (ROBOTIS e-Manual):

| รายการ | ค่า |
|---|---|
| ขนาด (ยาว × กว้าง × สูง) | 138 × 178 × 192 mm |
| ความเร็วเชิงเส้นสูงสุด | 0.22 m/s |
| ความเร็วเชิงมุมสูงสุด | 2.84 rad/s |
| เซนเซอร์ | LiDAR 360° (LDS-01 หรือ LDS-02), IMU |
| กล้อง | ไม่มี |
| คอมพิวเตอร์บนหุ่น | Raspberry Pi 4 |
| แบต | LiPo 11.1V 1800mAh ใช้งานได้ประมาณ 2 ชั่วโมง 30 นาที |

### 10.2 ผลต่อการออกแบบ
- **ขนาดช่อง**: `cell_size = 0.5 m` หุ่นกว้าง 0.178 m จึงมีระยะเผื่อให้ localization คลาดเคลื่อน
  แมพ 11×5 ต้องใช้พื้นที่ 5.5 × 2.5 m ถ้าพื้นที่ไม่พอ ลดเป็น 0.4 m (4.4 × 2.0 m) ได้
- **ความเร็ว**: ใช้ต่ำกว่าค่าสูงสุดเพื่อความแม่นยำ (ค่าเริ่มต้น 0.15 m/s, 1.0 rad/s)
  เดินหนึ่งช่องประมาณ 3–4 วินาทีรวมการหมุน การรันแบบ ADG ทำให้ไม่ต้องผูกเวลาจริงกับก้าวในแผน
- **แบตและสถานีชาร์จ**: TurtleBot3 ไม่มีแท่นชาร์จอัตโนมัติ และแบตจริงใช้ได้นานกว่าการสาธิต
  จึง **จำลองแบตใน Python ทั้งในซิมและหุ่นจริง** ช่องชาร์จบนพื้นจริงทำเครื่องหมายด้วยเทป
  หุ่นไปจอดที่ช่องนั้น แล้ว executor เพิ่มแบตตาม `charge_rate`
- **ไม่มีกล้องบนหุ่น**: localization ต้องใช้ LiDAR หรืออุปกรณ์ภายนอก (ดูหัวข้อ 12)

### 10.3 CoppeliaSim (ระดับ 2)
- เวอร์ชันที่ใช้: **CoppeliaSim 4.10.0 Edu** ฟิสิกส์ Bullet, dt 50 ms, ZMQ Remote API พอร์ต 23000
- เชื่อมจาก Python ผ่าน ZMQ Remote API ไม่ต้องใช้ ROS
- ใช้หุ่นล้อสองข้าง (differential drive) ตั้งขนาดและความเร็วสูงสุดให้ตรงกับ Burger ในตารางข้างบน
  เวลาและพฤติกรรมในซิมจะได้ใกล้ของจริง
- ในซิมใช้ตำแหน่งจริงจากซิมได้ แต่ต้องจำไว้ว่าหุ่นจริงจะมีความคลาดเคลื่อนจาก localization

### 10.4 TurtleBot3 จริง (ระดับ 3)
- ROS 2 Humble แต่ละตัวใช้ namespace ของตัวเอง เช่น `/tb3_0`, `/tb3_1` และ `ROS_DOMAIN_ID` เดียวกัน
- Backend `turtlebot_ros2.py` สร้าง node ด้วย `rclpy` ส่งคำสั่ง `geometry_msgs/Twist` ไปที่ `cmd_vel` ของแต่ละตัว
- ตัวควบคุมการเดินทีละช่อง: แนะนำให้เขียนเองแบบง่าย (หมุนให้ตรงทิศ แล้วเดินตรงจนถึงกลางช่อง)
  แทนการใช้ Nav2 เพราะคาดเดาได้ง่ายกว่าและไม่ต้องวางแผนเส้นทางซ้ำซ้อนกับ planner ของเรา
- ระวังเรื่องตั้งค่าหลายหุ่นใน ROS 2: namespace และ TF ของสองตัวต้องไม่ชนกัน
  ให้ทดลองเปิดหุ่นทีละตัวก่อน แล้วค่อยเปิดพร้อมกัน
- ตอนนี้ทำแค่ stub ตาม RobotInterface ลงมือจริงที่ M8

## 11. config.yaml (ตัวอย่างโครง)
```yaml
map: maps/challenge_11x5.txt
cell_size: 0.5            # เมตร ลดเป็น 0.4 ได้ถ้าพื้นที่จริงไม่พอ
robot:                    # TurtleBot3 Burger
  max_lin_vel: 0.22       # สเปกสูงสุด ห้ามเกิน
  max_ang_vel: 2.84
  cruise_lin_vel: 0.15    # ค่าที่ใช้จริง
  cruise_ang_vel: 1.0
ros2: {distro: humble, namespaces: [tb3_0, tb3_1]}
battery: {max: 40, move_cost: 2, wait_cost: 1, charge_rate: 5, min_final: 10, reserve: 0}
planner: {t_max: 200, priority: fixed, max_restarts: 10}
baseline: {threshold: 0.3}
experiments:
  n_scenarios: 50
  seed: 42
  priorities: [fixed, battery_urgency, random_restart]
  baseline_thresholds: [0.3, 0.5, 0.7, 1.0]   # 1.0 = ชาร์จเต็มก่อนทุกงาน
  reserves: [0, 5]
  delay_runs: 20                              # จำนวนรอบที่รันแบบมีความล่าช้าต่อแผน
  scaling:                                    # simulation เท่านั้น
    map: maps/loop_13x6.txt
    n_robots: [2, 3, 5]
    priority: random_restart
sim_delay: {enabled: false, prob: 0.2, max_extra_steps: 2}
scenario_gen: {n_robots: 2, battery_min: 10, tasks_min: 1, tasks_max: 3}
viz: {frame_ms: 500}
coppelia: {...}           # พอร์ต ขนาดหุ่นจำลอง และค่าตัวควบคุม ดูในไฟล์จริง
```

หมายเหตุ: `sim_delay.enabled` ยังไม่มีโค้ดส่วนไหนอ่าน ตัวรันการทดลองใช้ `experiments.delay_runs` แทน
จำนวนหุ่นไม่ได้ผูกไว้ที่ 2 ตัว มาจากไฟล์ฉากหรือ `scenario_gen.n_robots` ส่วนหุ่นจริงเพิ่มได้ที่ `ros2.namespaces`

## 12. คำถามที่ยังเปิดอยู่ (ห้ามเดา ให้ถามเจ้าของโปรเจค)
- กำหนดส่งงาน และอาจารย์กำหนดอัลกอริทึมจากในวิชาหรือไม่
- **วิธี localization ของหุ่นจริง** (ต้องตัดสินใจก่อน M8):
  - ก) LiDAR + AMCL บนแผนที่ที่สร้างด้วย SLAM: ใช้อุปกรณ์ที่มีอยู่ แต่ตั้งค่าหลายหุ่นยุ่งกว่า
  - ข) กล้องติดเพดานมองลงมา + ArUco marker บนหลังหุ่น: ได้ตำแหน่งบนกริดตรงๆ และแม่นยำ
    แต่ต้องมีกล้องและที่ติดตั้ง
- พื้นที่จริงที่ใช้ทดลองมีขนาดเท่าไร (ใช้ตัดสินขนาดช่อง 0.5 หรือ 0.4 m)
- หน่วยเวลาของ executor บน CoppeliaSim และหุ่นจริง: 1 ก้าวของแผนเท่ากับกี่วินาที
  (วัดใน CoppeliaSim ได้: เดินตรง 3.9 วินาที, เลี้ยว 90° ประมาณ 5.5 วินาที, กลับหลังหัน 7.6 วินาที)
- ค่า `battery.reserve` ที่จะใช้กับหุ่นจริง (ถ้าใช้ 5 แบตเริ่มของ R1 ใน S0 ต้องเป็น 21–23)

ตอบแล้ว:
- เวอร์ชัน CoppeliaSim: 4.10.0 Edu (หัวข้อ 10.3)
- แมพที่สอง: `maps/loop_13x6.txt` ใช้ใน simulation เท่านั้น (หัวข้อ 3)
- wait ที่ช่องชาร์จตอนแบตเต็ม: แบตคงที่ (หัวข้อ 4.1)
- รายละเอียดของ baseline (หัวข้อ 4.6) กฎการจอง (หัวข้อ 4.4) และแบตสำรอง (หัวข้อ 4.2)
